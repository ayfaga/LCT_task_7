## Инцидент «ML service failed» и исправление

Воспроизведены два состояния одной версии `origin/master` (`7b85efd`): с полным весом `model_inference.pt` ML `/ready` и backend `/ready` отвечают 200, а `/api/identify` обрабатывает изображение; с 135-байтным Git LFS pointer ML `/ready` отвечает 503, исходный backend возвращает общую ошибку `ML service failed`. Причина на машине разработчика **ещё должна быть подтверждена** проверкой файла/логов: это воспроизведённая причина, не прямой доступ к его компьютеру.

Исправлено в ветке `ml/local-startup-fix-20260927`:

1. Лёгкий `backend/artifact_preflight.py` до установки зависимостей и до загрузки Torch проверяет наличие manifest, полный вес, размер/SHA256 и путь к галерее; для LFS pointer выдаёт команду `git lfs pull`. Та же проверка выполняется в ML Docker-контейнере перед Uvicorn.
2. `quick_start.py` больше не создаёт фиктивную галерею, не переопределяет `LCT_ML_ARTIFACT_DIR`/`LCT_ML_GALLERY_PATH`, проверяет занятость портов, допускает `--backend-port`, `--ml-port`, `--skip-install`, ждёт готовности ML перед запуском backend и аккуратно останавливает только свои процессы. Убрано безусловное обновление системного pip.
3. HTTP gateway сохраняет 503, но отличает известные ошибки отсутствующих ML-артефактов/галереи и пишет статус upstream в лог вместо абсолютно немого `ML service failed`.

Проверки: финальный прогон `backend/tests` — 21/21 passed (четыре прежних предупреждения SQLAlchemy). Отдельная локальная end-to-end проверка на полном весе SHA256 `507b4f2e…da05f5` и реальной совместимой галерее из 750 снимков: ML `/ready` 200, backend `/ready` 200, `POST /api/identify` на исходном организаторском кропе с BBox полного кропа — HTTP 200, 10 ранжированных ID, версия `dinov2-l14-l336-joint-cityflow-organizer-best19-20260925`. Временные порты 18010/18011 остановлены. LFS pointer в чистом checkout отвергнут **до pip** с понятным сообщением. `docker compose config --quiet` успешен; Docker daemon на этом Mac не ответил, поэтому **новый контейнерный прогон после фикса не заявляется**. Никакой официальный mAP/F1/FPS этим smoke-тестом не измерялся.

### Очерёдность работы, без нового обучения модели

1. **P0 — снять баг у разработчика:** принять эту ветку, `git lfs pull`, проверить размер/SHA, задать путь к совместимой галерее, запустить venv/`quick_start`, проверить `/ready` и реальный `/api/identify`; если отличается — прислать статус `/ready` и traceback ML, не скрин одного `ML service failed`.
2. **P0 — сборка для жюри:** чистый Linux без доступа к интернету, заранее упакованные Docker-образы/веса и воспроизводимая галерея, запуск одной командой. Выход — протокол с checksum, версиями, `/ready`, положительным/отказным запросами и рестартом.
3. **P0 — воспроизводимость:** перенести именно финальные joint training/config/data-prep/eval/export исходники из исследовательского репозитория в публичный; обезличенные пути и отсутствие cookies/raw приватных данных; один README с точными командами и контрольными суммами. Пока это не сделано, риск дисквалификации остаётся даже при работающем API.
4. **P1 — данные и оценка:** реальная галерея/постоянное векторное хранение; три файла сдачи и официальный evaluator; mAP/R1/R5 по cross-camera, F1/TNR по объявленной единице, peak RAM/FPS на целевом железе. Все цифры — отдельно от smoke.
5. **P2 — tie-break:** миллионный ANN со сравнением точного top-10, error audit, attention; UI/дизайн ведёт фронтенд-команда.

До P0/P1 нельзя заявлять полное соответствие всем условиям. Исправление `ML service failed` возвращает работоспособный локальный путь и делает неполные артефакты явной ошибкой, но не заменяет отсутствующие элементы поставки.
