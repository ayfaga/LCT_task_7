# Ошибки финальной joint L336 на данных организатора · 27.09.2026

Выполнено локально на Mac с **замороженным** `model_inference.pt`
(`507b4f2e…34da05f5`) и `boosting_policy.json`
(`02578b92…6691d9`). Изменений веса, порога 0.44 или политики не было.
`objects.csv` SHA256 `c5eabdd4…c661d`; split SHA256
`2ea8a4ea…ab22f6d7f`. Holdout и test labels не открывались. Код и
машинно-читаемые выходы: `backend/ml/extract_joint_audit.py`,
`repro/audit_joint_errors.py`; локальные CSV/JSON не включают сами снимки.
Сводные результаты и SHA входов в Git:
[`joint_error_audit_mac_20260927.json`](joint_error_audit_mac_20260927.json).

## Протокол и знаменатели

Для retrieval каждый снимок dev/calibration — запрос; **все** снимки его
камеры исключены из галереи. mAP/Rank усредняются по валидным запросам.
Для open-set на каждом fold детерминированно выбраны known-ID и одна камера
каждого known-ID в галерею; остальные камеры known-ID и все unknown-ID —
запросы. Все resolution/brightness/sharpness-срезы используют **одну и ту же
галерею внутри fold**. F1 ниже — micro-F1 по парам query–candidate,
TNR — доля unknown-запросов без принятого кандидата; это proxy, не
официальная метрика жюри. Один ID имеет несколько запросов, поэтому
приведены также macro-TNR и число затронутых ID.

**Важно:** calibration использовалась для обучения калибратора. Её F1/TNR
в этом аудите — применение окончательного fitted booster к тем же ID,
**не OOF и не независимая оценка**. Первоначальный выбор порога выполнялся
через ID-group OOF; здесь мы разбираем поведение поставляемого runtime,
а не повторяем OOF. Dev тоже многократно использовалась в исследованиях:
это exploratory readout, не новый sealed test. Retrieval mAP не зависит
от калибратора. Ни одну из этих метрик нельзя выдавать за hidden-score.

| Показатель | dev (exploratory) | calibration (fitted-policy readout) |
|---|---:|---:|
| Full-fold cross-camera queries | 1 449 | 929 |
| mAP | 73,1528% | 80,3063% |
| Rank-1 / Rank-5 | 73,5680% / 86,8185% | 81,7008% / 93,1109% |
| Open-set gallery / queries / known queries | 413 / 1 036 / 603 | 277 / 652 / 365 |
| Pair micro-F1 / unknown-query TNR | 58,7382% / 77,5982% | 69,9467% / 77,7003% |
| Unknown-ID macro-TNR | 78,0969% | 78,8652% |
| False accept unknown / false reject known / wrong accept known | 97 / 178 / 45 | 64 / 88 / 11 |

Dev mAP 0.7315276 отличается от прежней A100 FP32 оценки 0.7315318 на
0.0000042 абсолютной доли; pair-F1 0.587382 совпал с опубликованным ранее
значением до округления. Calibration mAP 0.8030633 отличается от прежнего
A100 0.8031780 на 0.0001147 абсолютной доли (0.0115 п.п.); это совместимо
с различием между локальным frozen inference и исходным extraction-путём,
но точная причина не установлена. Это сильная проверка локального пути, не
доказательство официального evaluator.

`false_reject_known` — ни один кандидат не принят при наличии правильного
ID в галерее. `wrong_accept_known` — приняты только чужие ID, хотя свой
есть. `false_accept_unknown` — принят кто-либо, когда своего ID в галерее
нет. Остальные 716 dev-запросов — правильное принятие известного или
правильный отказ неизвестному; в CSV это явно разделяется полями
`known`/`correct_id_accepted`. На calibration из 88 полных отказов known
в 39 случаях top-1 ID тоже правильный; ложные принятия unknown приходятся
на 17 уникальных ID. TNR по запросам почти одинаков на dev/calibration
(77.60/77.70%), однако доля ошибочных known-принятий различается, поэтому
одно число F1 не описывает весь профиль ошибок.

## Что видно на dev

- Из 178 полных отказов известным автомобилям в **95** случаях top-1 ID
  правильный, но cosine ниже порога; это ошибка механизма отказа, а не
  топ-1 retrieval. Верхний квартиль их cosine 0.4165, максимум 0.4398
  непосредственно под фиксированным порогом 0.44. Менять порог по этому
  dev-аудиту нельзя без независимой проверки TNR/F1.
- 97 ложных принятий unknown относятся к **29 уникальным ID**, а не к 97
  разным автомобилям. Например, ID 445 шесть раз сопоставляется с ID 1258;
  исходные кропы `847af126…` и `0f818cbe…` визуально показывают два
  похожих тёмных внедорожника одного семейства, один частично перекрыт
  столбом. Это иллюстрация визуального сходства, не заявление об ошибке
  разметки или причине работы модели.
- Wrong accept известного ID 711 → 1524 при cosine 0.7089:
  `5b0811a0…` и `b91df38d…` — визуально крайне похожие автомобили одной
  модели с похожей раскраской. Для сравнения `7f6a29c0…` — другой ракурс
  истинного ID 711. Внешнее сходство объясняет трудность задачи; по
  снимкам нельзя уверенно утверждать, что IDs ошибочны.
- Корректный top-1, но отказ на границе: ID 595, query
  `a3782d37…`, gallery `80852bdc…`, cosine 0.439267. Ракурс существенно
  отличается (задняя боковая сторона против переда). Это конкретный
  пример trade-off порога, не основание подстроить его по одному случаю.

По размеру native crop dev: `<256px` всего 11 запросов (6 known),
`256–383px` 131 (82 known), `≥384px` 894 (515 known).
Top-1 accuracy на known соответственно 50.0%, 67.1%, 76.7%, но первый
срез слишком мал; это наблюдение, не устойчивая зависимость. Фальшивые
unknown accept-rate по этим срезам 20.0%, 16.3%, 23.2%: нет монотонного
улучшения отказа с ростом размера. Brightness/sharpness — EDA-прокси, не
размеченные условия съёмки. Ракурс и перекрытие **не имеют достоверных
меток**; никаких чисел «по ракурсу/окклюзии» не заявляем.
На calibration срез `<256px` содержит **один** known-запрос, поэтому его
100% top-1 не имеет смысла сравнивать с dev. Для `256–383px` и `≥384px`
calibration top-1 известного ID 90.3% (62 запроса) и 81.1% (302 запроса):
направление противоположно dev. Значит, имеющихся срезов недостаточно для
устойчивой гипотезы «ниже разрешение ⇒ хуже» на наших данных.

## Локальное воспроизведение

При наличии организаторских crop PNG на диске:

```sh
.venv-test/bin/python backend/ml/extract_joint_audit.py \
  --artifact-dir model_artifacts/joint_l336 \
  --objects /absolute/path/to/objects.csv \
  --splits repro/configs/identity_splits.json \
  --crops /absolute/path/to/crops --fold dev \
  --output /absolute/path/to/dev_features --device cpu --threads 4
.venv-test/bin/python repro/audit_joint_errors.py \
  --objects /absolute/path/to/objects.csv \
  --splits repro/configs/identity_splits.json \
  --features /absolute/path/to/dev_features/features.npz \
  --fold dev --policy model_artifacts/joint_l336/boosting_policy.json \
  --output /absolute/path/to/dev_error_audit
```

Повторить с `--fold calibration` в **других** output-каталогах. Скрипты
отказываются перезаписывать существующие результаты. Получаются
`summary.json`, `slices.json`, per-query retrieval/open-set CSV,
`open_set_identities.csv` и `error_examples.csv` с image_id для просмотра
оригинальных organizer-кропов. Публичный Git содержит только код/выводы,
не сами изображения или эмбеддинги dev/calibration.

Attention-карта из `backend/ml/visualize_last_attention.py` — реальная
матрица последнего CLS→patch attention. Она может иллюстрировать пример,
но **не** является причинным объяснением wrong match или отказа. Локально
построены карты для обычного кропа, wrong-accept 711→1524 и false-reject
595; визуально высокие значения распределены по кузову и частично по фону,
поэтому из них нельзя делать вывод, что конкретная деталь вызвала ошибку.
