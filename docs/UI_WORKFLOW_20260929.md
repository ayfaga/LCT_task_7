# Одна галерея и два режима поиска · 29.09.2026

После синхронизации с `origin/master` `2ec5b44` пользователь уточнил
сценарий: галерея поиска одна для обоих режимов. Главная `/` показывает
сначала её состояние и загрузку, затем два способа отправить запрос:

| Экран | Ввод | Действие |
| --- | --- | --- |
| `/gallery` | JPEG/PNG или ZIP, опциональный BBox CSV | `POST /api/common-gallery/images`; ожидание индексации общей галереи |
| `/solo` | один JPEG/PNG + прямоугольник на исходном кадре | `/api/infer` с общим `gallery_id`, BBox в исходных пикселях, JSON результата |
| `/many` | группа JPEG/PNG + обязательный `image_id,x,y,w,h` CSV | `/api/infer` для каждого запроса с тем же `gallery_id`, CSV результатов |

После поиска оба режима показывают все возвращённые top-10 кандидатов с
фото автомобиля, ID и cosine-сходством. Нажатие на любое фото открывает
крупный просмотр с переключением между кандидатами и ссылкой на исходный
кадр. Это **не вероятности**: cosine показан как мера сходства, а принятие
или отказ остаются решением ML-политики. Для галереи с BBox фото кандидата
формируется из сохранённого полного кадра и его BBox по запросу; crop
кэшируется на диске. Ответ `/api/infer` дополняется `image_url` и
`source_image_url` для каждого найденного ID в той же галерее. Кнопка JSON
экспорта в одиночном режиме выровнена по правому краю нижней строки окна.

Эта доработка проверена локально: 42 backend и 12 frontend тестов, визуальный
прогон `/solo` с десятью кандидатами и просмотром каждого изображения через
backend-only стенд с заглушкой поиска. Настоящий DINO-инференс и Windows
этот прогон не подтверждает; вес и порог отказа не менялись.

`GET /api/common-gallery` возвращает состояние без создания файлов; первая
загрузка создаёт фиксированную общую галерею. Поиск доступен после индексации
минимум 10 изображений. Старые пользовательские галереи и опциональная
read-only NPZ-галерея не удаляются и автоматически не смешиваются с новой:
они остаются доступны прежним API, а новый UI использует только общую.

Галерея из уже обрезанных автомобилей загружается без CSV. Для полных кадров
нужен BBox CSV с `image_id,x,y,w,h` либо
`filename,gallery_id,x,y,w,h`. Можно приложить полный CSV организатора,
даже когда загружается только часть его изображений: backend выбирает
нужные строки по точному пути, затем по имени файла и основе без расширения.
Корневой каталог внутри ZIP может отличаться от пути в CSV. Лишние строки
игнорируются; отсутствие или неоднозначность BBox для загруженного кадра
даёт явную ошибку, без молчаливого перехода к полному кадру. ZIP принимает
внешний CSV или `manifest.csv` внутри архива. Без CSV backend сознательно
индексирует весь кадр. Имена/ID должны быть уникальными. Фиксированные
лимиты на количество и байты импорта сняты; файлы копируются из ZIP на диск
по одному. Ограничение по свободному диску, 50 Мп для защиты декодера и
фактическим ресурсам индекса остаётся. Для многогигабайтного архива
организатора предпочтителен возобновляемый CLI из
`docs/ORGANIZER_ARCHIVE_IMPORT.md`.

Пакетный поиск `/many` принимает отдельные JPG/PNG, выбранную папку
(`webkitdirectory`, включая вложенные папки) или ZIP. Для всех вариантов
можно приложить полный BBox CSV; лишние строки игнорируются. Папка
сопоставляется в браузере, ZIP — на сервере. В ZIP каждый кадр извлекается
во временный файл и последовательно отправляется в ML-сервис; весь архив
не распаковывается в RAM и 20-МиБ лимит на файл для этого пути не нужен.
Остаются ограничения свободного диска, 50 Мп при декодировании и времени
ответа; при повреждённом BBox запрос не отправляется модели. ZIP-путь
возвращает результаты разом после обработки, пока без пофайлового прогресса.
Новый маршрут: `POST /api/infer-batch` с `archive`, `manifest`,
`gallery_id`, `topk`.

После этой доработки прошли 46 backend- и 11 frontend-тестов. На реальных
примерах `gallery_full_frames.zip`+`gallery_bbox.csv` и
`query_full_frames.zip`+`query_bbox.csv` сопоставление дало 10/10 и 2/2
кадра соответственно. Настоящий DINO-инференс/Windows этим не проверялись.

29.09 regression: `data/example_upload_full_frames/gallery_full_frames.zip`
плюс `gallery_bbox.csv` прошли через `POST /api/common-gallery/images`:
HTTP 202, 10 записей с точными путями `images/*.jpg` и BBox. На машине
разработчика эту же пару раньше блокировал UI. Проверка использовала
заглушку фонового ML build; полный прогон с настоящим весом не заявляется.

Legacy `/replenishment` и его данные не удалены, но этот маршрут только
сохраняет файлы и не строит поисковый индекс. Он больше не показан на главной.

На первом этапе интерфейса прошли 38 Python-тестов и 8 Node-тестов;
главная и галерея были осмотрены в браузере на широком и узком экране.
Актуальные числа после доработки результатов приведены выше.
Ручное выделение на исходном изображении проверялось в предыдущей версии
интерфейса. Это проверка UI/API, **не** end-to-end поиск настоящей моделью.
Docker Desktop и ML-сервис на момент проверки не работали; индексацию и оба
режима поиска через полный стек нужно повторить после его запуска.
Модель/веса/политика отказа не менялись.
