# Одна галерея и два режима поиска · 29.09.2026

После синхронизации с `origin/master` `2ec5b44` пользователь уточнил
сценарий: галерея поиска одна для обоих режимов. Главная `/` показывает
сначала её состояние и загрузку, затем два способа отправить запрос:

| Экран | Ввод | Действие |
| --- | --- | --- |
| `/gallery` | JPEG/PNG или ZIP, опциональный BBox CSV | `POST /api/common-gallery/images`; ожидание индексации общей галереи |
| `/solo` | один JPEG/PNG + прямоугольник на исходном кадре | `/api/infer` с общим `gallery_id`, BBox в исходных пикселях, JSON результата |
| `/many` | группа JPEG/PNG + обязательный `image_id,x,y,w,h` CSV | `/api/infer` для каждого запроса с тем же `gallery_id`, CSV результатов |

`GET /api/common-gallery` возвращает состояние без создания файлов; первая
загрузка создаёт фиксированную общую галерею. Поиск доступен после индексации
минимум 10 изображений. Старые пользовательские галереи и опциональная
read-only NPZ-галерея не удаляются и автоматически не смешиваются с новой:
они остаются доступны прежним API, а новый UI использует только общую.

Галерея из уже обрезанных автомобилей загружается без CSV. Для полных кадров
нужен manifest `filename,gallery_id,x,y,w,h`. При выборе отдельных JPEG/PNG
страница может преобразовать стандартный CSV организатора
`image_id,x,y,w,h` в этот manifest; для ZIP нужен готовый `manifest.csv`
внутри архива или отдельным файлом. Без manifest backend сознательно
индексирует весь кадр. Имена/ID должны быть уникальными. Фиксированные
лимиты на количество и байты импорта сняты; файлы копируются из ZIP на диск
по одному. Ограничение по свободному диску, 50 Мп для защиты декодера и
фактическим ресурсам индекса остаётся. Для многогигабайтного архива
организатора предпочтителен возобновляемый CLI из
`docs/ORGANIZER_ARCHIVE_IMPORT.md`.

29.09 regression: `data/example_upload_full_frames/gallery_full_frames.zip`
плюс `gallery_bbox.csv` прошли через `POST /api/common-gallery/images`:
HTTP 202, 10 записей с точными путями `images/*.jpg` и BBox. На машине
разработчика эту же пару раньше блокировал UI. Проверка использовала
заглушку фонового ML build; полный прогон с настоящим весом не заявляется.

Legacy `/replenishment` и его данные не удалены, но этот маршрут только
сохраняет файлы и не строит поисковый индекс. Он больше не показан на главной.

Проверено локально без ML-сервиса: 38 Python-тестов и 8 Node-тестов;
главная и галерея осмотрены в браузере на широком и узком экране.
Ручное выделение на исходном изображении проверялось в предыдущей версии
интерфейса. Это проверка UI/API, **не** end-to-end поиск настоящей моделью.
Docker Desktop и ML-сервис на момент проверки не работали; индексацию и оба
режима поиска через полный стек нужно повторить после его запуска.
Модель/веса/политика отказа не менялись.
