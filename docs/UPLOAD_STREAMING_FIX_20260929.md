# ZIP + BBox CSV и потоковая загрузка · 29.09.2026

## Причина и исправление

1. UI запрещал отдельный CSV при выбранном ZIP, хотя backend принимает
   `archive` + `manifest`. Теперь оба файла можно выбрать одновременно.
   Для ZIP `filename` должен включать путь внутри архива, например
   `images/f0d68....jpg`. Сопоставление проверяется до распаковки; при ошибке
   API показывает первые недостающие/лишние пути.
2. Backend читал ZIP и каждый JPEG/PNG целиком в `bytes`, а затем держал
   копии всех изображений в списке. Это могло вызвать `MemoryError` на
   Windows. Теперь FastAPI spool передаётся прямо в `ZipFile`, файлы
   извлекаются на диск по одному чанками 1 МиБ, проверяются по одному и
   атомарно переходят в persistent gallery. Тяжёлая подготовка выполняется
   в worker thread. Аналогично поисковый запрос пересылается в ML сервис
   потоком из upload spool, без второго `bytes`-буфера.

Фиксированные лимиты 20/100/200 МиБ и 200/1000 изображений для пути
галереи убраны. Это **не** означает бесконечную вместимость: при нехватке
диска возвращается HTTP 507 с резервом 256 МиБ; для безопасности декодера
кадр ограничен 50 Мп. Большой точный индекс всё ещё требует RAM и времени;
его пределы на реальных больших галереях отдельно не измерены. Для
многогигабайтного архива организатора лучше использовать возобновляемый CLI.
Ответ статуса передаёт истинный `image_count`, но не более 100 последних
превью (`images_truncated=true`), чтобы не раздувать JSON при большой базе.

## Проверка

- `gallery_full_frames.zip` (5.8 МиБ) + `gallery_bbox.csv` (680 байт) из
  `data/example_upload_full_frames`: HTTP 202, 10 pending-изображений,
  полный путь `images/...jpg` и BBox совпали с CSV.
- Те же реальные 10 кадров прошли построение индекса через тестовый энкодер:
  `search_ready=true`, 10 объектов, BBox всех строк совпали, top-1 ID `403`.
  Это интеграционная проверка конвейера, не метрика настоящей модели.
- Тесты: 41 Python и 10 JS успешно; в том числе ZIP+отдельный CSV с вложенными
  путями и проверка UI-выбора двух файлов.
- Docker daemon локально недоступен; полный прогон с настоящим весом и
  Windows-машина бэкендера **не проверены**.

Для проверки у бэкендера: обновить эту ветку, перезапустить backend и ML,
открыть `/gallery`, выбрать ZIP и CSV одновременно, дождаться «Готова к
поиску». Затем распаковать `query_full_frames.zip`, открыть `/many`, выбрать
2 JPG и `query_bbox.csv`. При повторном `MemoryError` прислать полный
traceback начиная с вызова в `app/`, статус свободной RAM/диска и точный
endpoint; фрагмент только из `tempfile.py` не указывает однозначно на путь.
