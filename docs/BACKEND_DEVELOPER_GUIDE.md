# Памятка backend-разработчику: E2 ReID API

Этот документ описывает локальный MVP в ветке `ml/e2-boosting-integration`.
Модель пока прототипная; после дообучения потребуется новый комплект артефактов.
Приватная страница для ручной проверки хранится вне этого репозитория и в
ветку не входит.

## Что где находится

- `backend/app/main.py` — публичное FastAPI-приложение. Принимает запрос,
  валидирует BBox и вызывает ML по HTTP.
- `backend/app/ml_gateway.py` — единственная точка связи backend с ML.
- `backend/app/ml/` — изолированный ML-сервис: preprocessing, DINOv2-L/14,
  точный cosine-поиск и политика отказа `shallow5`.
- `backend/app/gallery_store.py` — валидация загружаемых изображений, метаданные
  пользовательских галерей и исходные файлы.
- `docker-compose.yml` — два контейнера (`backend`, `ml`) и общий постоянный
  том `gallery_state`. Backend и ML не делят Python-процесс; ML вызывается по
  внутреннему HTTP.

Backend не загружает Torch или веса. Модель и стандартная gallery на 750 фото
подключаются к ML-контейнеру read-only с хоста. Пользовательские изображения
и версии NPZ-индексов сохраняются в `gallery_state` и переживают пересоздание
контейнеров.

## Запуск и проверка готовности

Из каталога `LCT_task_7`:

```sh
LCT_BACKEND_PORT=18000 LCT_ML_PORT=18001 docker compose up --build -d
docker compose ps
curl -fsS http://127.0.0.1:18000/ready
```

Для стандартной конфигурации артефакты должны лежать относительно Compose-файла
в `../data/derived/final_e2_hybrid/` и `../data/derived/final_e2_hybrid/test_gallery_e2.npz`.
Для другого расположения задайте абсолютные `LCT_ML_ARTIFACT_DIR` и
`LCT_ML_GALLERY_PATH`. API документация доступна на `/docs`.

## API контракты

### Инференс

`POST /api/identify` (совместимые aliases: `/api/infer`, `/v1/search`) принимает
multipart поля `image`, `x`, `y`, `w`, `h`; дополнительно доступны `topk`
(1–100) и необязательный `gallery_id`. Координаты BBox — пиксели исходного
изображения. JPEG/PNG, максимум 20 MiB. Для embeddings есть
`POST /v1/embeddings` с теми же полями изображения и BBox.

Ответ поиска:

- `ranked` — cosine top-N;
- `accepted` — кандидаты, прошедшие отказ; `candidates` оставлен как alias;
- `status=matched` или `no_confident_match` (отказ возвращается HTTP 200);
- `confidence` и `similarity` — raw cosine, не вероятность;
- `model_version` и `gallery_id` связывают ответ с версией модели/галереи.

Политика отказа применяется к внутреннему cosine top-10 даже при `topk<10`.
Для текущего прототипа пороги `.394` и `.112` специфичны для выбранной модели;
при переобучении их нельзя переносить без новой калибровки.

### Пользовательские галереи

| Метод и путь | Назначение |
|---|---|
| `POST /api/galleries` | Создать галерею, multipart `name`; ответ 201 с UUID |
| `GET /api/galleries` | Список галерей и их состояния |
| `GET /api/galleries/{id}` | Состояние, счётчик, прогресс и превью-файлы |
| `POST /api/galleries/{id}/images` | Импорт файлов или ZIP; ответ 202, обработка в фоне |
| `POST /api/galleries/{id}/retry` | Повторить импорт после `failed` |
| `GET /api/galleries/{id}/images/{image_key}` | Получить исходный загруженный файл |

Импорт принимает повторяющееся multipart-поле `images` **или** одно `archive`
(ZIP); дополнительно можно передать `manifest` CSV. В ZIP допускается
`manifest.csv` в корне. Имена CSV должны соответствовать именам загруженных
файлов; колонки: `filename,gallery_id,x,y,w,h`. Без CSV файл считается готовым
кропом машины, а ID берётся из имени файла. BBox в CSV нужен для полного кадра.

Ограничения: 1–200 файлов на импорт, 20 MiB на изображение, 100 MiB ZIP,
200 MiB суммарно на импорт, 1000 фото на галерею. Для поиска нужно минимум
10 обработанных фото: политика отказа использует top-10. Импорт ZIP проверяет
типы изображений, пути, размеры, дубликаты и манифест. Статус `building`
показывает фоновый пересчёт; ошибка переводит импорт в `failed`.

Из backend ML вызывается на `POST /internal/galleries/{id}/build`; endpoint
доступен через внутреннюю Compose-сеть. Не выставляйте его наружу.

### Ошибки и готовность

Невалидные изображения/BBox — 422, превышение лимита — 413, неизвестная
галерея — 404, неготовая пользовательская gallery для поиска — 409,
недоступная ML/артефакты — 503. `/health` проверяет процесс backend;
`/ready` дополнительно проверяет БД и ML.

## Важное при замене модели

Сохраняйте новый checkpoint в отдельной versioned-папке. Для него нужны
совпадающие manifest/preprocessing/policy и свежие embeddings всей галереи.
Runtime сверяет модель и галерею по версии и SHA. Старые веса, gallery NPZ,
booster и пороги оставьте как rollback. Сначала запустите новый комплект и
проверьте `/ready`, запросы с известным результатом и отказ, затем переключайте
Compose на новые пути. Сейчас один ML-контейнер: обновление с его перезапуском
может кратко прервать запросы. Blue-green rollout и автоматический rollback
пока не настроены.

## Проверки и границы MVP

В `backend/tests` — 10 тестов: API-контракт, проверки ошибок, загрузка ZIP и
файлов, построение индекса, поиск и восстановление. Также локально проверены
оба Docker-контейнера и сохранность пользовательской gallery после restart.
Это локальный CPU-прототип, а не испытание на сервере жюри.

Текущий пользовательский индекс — версионированный NPZ с точным NumPy cosine,
подходит для тестовой галереи порядка 750 фото и ручных наборов до 1000 фото.
Постоянный векторный индекс/БД для большого каталога, официальный batch/FPS
benchmark, целевой Linux/GPU deployment и безостановочная смена модели
остаются дальнейшей backend-работой. Полный аудит требований —
[`CRITERIA_AUDIT_20260924.md`](CRITERIA_AUDIT_20260924.md).
